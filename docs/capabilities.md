# 기능(capability)

이 문서는 기능 하나를 어디에 어떻게 더하는지에 대한 정본이다. 규칙은 문장이 아니라
`bin/smoke.mjs` 와 `test/` 의 검사가 강제한다. 아래 각 항목 뒤의 괄호가 그 검사 이름이다.
따라 할 절차는 `docs/extending.md` 에 있다.

## 기능과 앱 셸의 구분

앱은 항상 로드되는 앱 셸(shell)과, 사용자가 켜고 끌 수 있는 기능(capability)으로 나뉜다.

앱 셸은 `web/js/main.js` 에서 정적으로 참조되는 모든 것이다. 스페이스·터미널·탭·브라우저처럼
없으면 앱이 성립하지 않는 부분이다. 파일 수는 여기 적지 않는다. 적어 두면 코드가 바뀔 때마다
그 줄이 실제와 어긋나기 때문이고, 현재 값은 검사가 계산한다.

가운데·브라우저 탭 띠·본문의 외부 파일 열기는 `center/file-drop.js`가 맡는 앱 셸이다. 가운데는
기존 `openFile`, 브라우저는 `openDroppedLocal`로 보내 등록된 뷰어 또는 기존 `file://` 탭으로 연다.
게스트 페이지가 처리하지 않은 외부 파일은 webview preload의 `ac-file-drop` IPC로 받는다.
페이지가 드롭을 처리하거나 업로드·입력 칸에 놓으면 게스트에 양보한다.
터미널의 경로 삽입은 계속 `chatcopy` 기능이 맡는다. native 다리
`acHost.getDroppedPath`는 두 경로가 공유하므로 "채팅 복붙을 틀이 모른다" 검사는 가운데 드롭
모듈의 이 이름만 허용한다. 채팅 복붙을 꺼도 가운데에서 파일을 열 수 있다.

`node bin/smoke.mjs`의 브라우저 드롭 검사는 별도 임시 프로필의 headless Chrome/Chromium에서
실제 CDP 드롭 사건을 보낸다(`CHROME_BIN`으로 실행 파일 지정 가능). Iris 앱이나 사용자 프로필을
조작하지 않는다. Electron의 IPC·파일 경로 API는 이 검사에서 대역이므로 설치 앱 확인은 별도다.

기능은 `web/js/core/capabilities.js` 표에 한 항목으로 등록되고 동적 import 로만 로드된다. 끄면
그 모듈은 로드되지 않는다("켠 것만 싣는다는 말이 실제로 성립한다").

기능의 범위는 rail 화면보다 넓다. rail 에 등록되는 기능도 있고, 사이드바 슬롯 하나만 갖는
기능도 있으며(실행), rail 도 슬롯도 없이 가운데 탭이나 터미널 위에만 붙는 기능도 있다(표·문서
뷰어 · 채팅 복붙 · Chrome 넘기기 · 로그인 저장). rail 이 없는 항목은 rail 표에서 이름을 가져올
수 없으므로 `label` 을 직접 갖고, 앱 셸이 `web/index.html` 에 이미 그려 둔 슬롯을 쓰면 그
element id 를 `panel` 로 갖는다. 화면이 없으므로 `screen` 도 돌려주지 않는다. 돌려주면 진입
경로가 없는 화면이 된다("rail 없는 기능은 이름을 갖고 화면을 갖지 않는다").

`panel` 이라는 용어는 두 표에서 서로 다른 것을 가리킨다. 등록표(`web/js/core/capabilities.js`)의
`panel` 은 앞 문단의 그것으로, 앱 셸이 index.html 에 그려 둔 도크·띠 영역이며 그 id 의 실물이
index.html 에 있어야 한다("끈 기능의 자리는 실제로 내려간다"). rail 표(`web/js/core/rail-items.js`)
의 `panel` 은 rail 화면의 영역이고, `devtool/rail.js` 의 `registerPanel` 이 로드할 때 만들어
`panelHtml` 을 채운다. index.html 에 함께 두면 두 벌이 되므로 검사가 막는다("표의 각 줄이 실물과
이어져 있다"). 새 rail 화면의 영역은 rail 표에만 적는다.

영역을 둘 갖는 항목도 있다. 사용량이 창 아래 띠(`panel: "statusbar"`)와 rail 화면
(`rail: "usage"`)을 한 항목으로 함께 갖는다. 둘이 같은 자료를 보여 주기 때문에 두 항목으로
나누지 않는다. 띠 아래의 「사용량 상세·이력」 줄이 그 화면으로 가는 진입 경로이므로, 따로 끄고
켤 수 있게 두면 진입 경로가 없는 화면을 가리키게 된다. rail 이 있는 항목은 이름을 rail 표에서
가져오므로 `label` 을 따로 갖지 않는다.

기능이 어느 창에서 로드되는지도 표가 밝힌다. 창은 본 창 · 분리 브라우저 창 · 메모 창 셋이다.
같은 페이지를 다른 mode 로 여는 구조라서, 표에 적지 않은 기능은 그 창에서 로드되지 않는다.

```js
windows: ["main", "browser"],   // 안 적으면 본 창에서만
alwaysIn: ["memo"],             // 그 창에서는 사람이 껐어도 싣는다(그 기능이 곧 그 창일 때)
```

이 판정을 main 이 직접 갖고 있으면 창을 하나 더 만들 때마다 앱 셸을 수정해야 한다
("기능이 사는 창을 표가 밝힌다").

켜짐·꺼짐 상태의 소유자는 상태 폴더의 `features.json` 이다. `server/feature-state.js` 가 그것을 쓰고,
`server/feature-state-read.cjs` 를 서버와 네이티브가 함께 읽는다. 렌더러는 부팅에서
`GET /features` 로 먼저 읽고, `web/js/core/features.js` 가 두 표를 합쳐 설정 화면이 그릴 목록을
하나 만든다. `devtool/rail.js` 는 그것을 화면에 반영만 한다. 표에 항목을 추가하면 그 목록에
자동으로 등록된다. 검사는 `featureList()` 를 직접 불러 모든 기능 id 가 있고 이름이 비지 않았는지만
본다("표의 모든 기능이 설정 목록에 선다"). 그 항목이 실제 화면에 그려지는지는 검사하지 않는다.

저장은 `PUT /features` 하나로만 한다. 로컬(127.0.0.1) 연결만 쓸 수 있고, 보낸 `baseRevision` 이
현재 것과 다르면 409 로 거절한다. 거절당한 쪽은 돌아온 최신 상태에 자기 변경을 다시 얹어
보내므로, 두 창이 동시에 바꿔도 서로의 변경이 남는다. 상태를 읽지 못하면 무엇이 꺼져 있는지
알 수 없으므로 선택 기능을 하나도 로드하지 않은 채로 뜨고, 설정 변경이 잠긴다.

## 기능 추가 절차

따라 할 절차는 `docs/extending.md` 에 있다. 여기서는 어느 표에 무엇을 등록하는지만 적는다.

1. 화면이 있으면 `web/js/core/rail-items.js` 에 한 줄. id·이름·아이콘·body class·패널·배치·
   내릴 수 있는가. `web/index.html` 의 rail 버튼도 같은 것을 말해야 한다("rail 마크업이 표에서
   그린 것과 같다". 표에서 그린 글자를 그대로 붙이면 된다).
2. `web/js/core/capabilities.js` 에 한 줄.
   ```js
   // rail 화면이면: 영역은 rail 표가 갖는다. 이 표의 panel 은 비운다
   { id, rail, files: ["어디/그것.js"], css: ["33-그것.css"],
     load: () => import("../어디/그것.js") }
   // rail 없이 앱 셸의 도크 영역만 쓰는 기능이면: 그 id 는 index.html 에 실물이 있어야 한다
   { id, label: "실행", panel: "panel-run", files: [...], css: [...], load: ... }
   ```
   연결은 표에 적지 않는다. 로드된 모듈이 `initCapability(ctx)` 를 내주고 `{ screen, ws }` 를
   돌려주며, rail 화면을 갖는 기능은 `panelHtml` 로 그 영역의 안쪽 마크업을 함께 들고 온다.
   검사가 입구 파일만 보므로 `panelHtml` 은 입구 파일이 다시 `export` 해야 한다.
3. CSS 는 `web/css/` 에 자기 파일로 두고 `web/index.html` 에 번호순으로 로드한다. rail 화면의
   영역은 `panelHtml` 이 들고 오므로 `index.html` 에 또 두지 않는다(두 벌이 된다). 그 영역의
   폭도 이 CSS 가 갖는다. rail 표에 `panel` 이 있는 항목은 그 기능의 CSS 에
   `.<panel> { width: … }` 가 있어야 하고, `web/css/03-feature-modes.css` 가 그 폭을 가지면
   검사가 막는다("화면 폭은 그 화면의
   지면이 갖는다").
4. `initCapability` 가 꺼내 쓰는 것은 `main.js` 의 `bootCapabilities({ ctx })` 에 있어야 한다
   ("기능이 꺼내 쓰는 이름을 main 이 실제로 준다").
5. 서버 쪽 구현이 있으면 `server/capabilities.js` 에 같은 id 로 한 줄을 등록하고 렌더러 표에는
   `server` 로 그 파일을 밝힌다. 네이티브 쪽이면 `native/electron/capabilities.cjs` 에 한 줄,
   렌더러 표에는 `native: true`("서버·네이티브 표의 행은 렌더러 표에 server·native 로 적혀
   있다 — 재시작 안내가 그 표시로 판정한다").

## 독립 화면을 갖는 기능

기능이 항상 `web/js/` 아래 모듈인 것은 아니다. 자기 HTML 한 장을 통째로 갖고 서버가 그대로
내주는 화면도 있다(메모랩). 그런 기능은 표 항목에 두 필드를 더 갖는다.

```js
{ id: "memolab",
  files: ["devtool/memolab-screen.js"],       // 셸 쪽 입구. iframe 을 붙이는 위치다
  page: "web/memolab",                        // 이 기능이 통째로 갖는 화면 디렉터리
  routes: ["/memolab-state", "/memolab-ui"],  // 그 화면이 쓰는 HTTP 경로
  server: ["server/memolab-store.js"] }
```

소유는 원래 `web/js` 아래 모듈(`files`)과 WebSocket 메시지 이름 두 가지로만 표현됐다. HTTP 로만
동작하는 기능은 그 둘 중 어느 것으로도 자기 소유를 표현할 수 없어서, 서버 파일을 정확히 적어
놓고도 그 기능의 것이 아니라는 판정을 받았다.

`routes` 는 서버 소유의 두 번째 근거다("기능의 서버 쪽 반을 표가 밝힌다"). 다만 적는 것만으로는
성립하지 않고, 라우터가 그 경로를 실제로 받고 그 자리에서 이 기능이 적은 서버 파일이 내준
처리기를 호출할 때만 성립한다.

`page` 는 네 방향으로 대조한다("독립 지면과 HTTP 경로도 기능이 소유한다").

- 그 디렉터리가 실재하고 비어 있지 않은가
- 앱 셸이나 다른 기능이 그 안을 정적으로 참조하지 않는가(독립의 정의)
- 밝힌 경로가 라우팅되고 그 처리기가 이 기능의 서버 파일에서 나오는가
- 그 화면이 실제로 그 경로를 호출하는가(아무도 호출하지 않는 경로는 죽은 경로다)

같은 경로를 두 기능이 적는 것도 여기서 막는다. 나중에 등록된 쪽이 조용히 이기기 때문이다.

독립 화면은 렌더러 검사 대상 파일 집합(셔틀)에서 제외한다. 앱 셸이 아닌데도 「이 모양이 어디에도
없어야 한다」는 부정형 검사들이 다른 기능의 화면까지 검사하기 때문이다. 제외하면 검사되지 않는
영역이 되므로 전용 검사 절이 그만큼을 대신 맡아 화면 파일을 세어 제외 목록과
대조한다("셔틀에서 뺀 지면은 이 절이 그대로 받는다"). 화면에 파일을 하나 더하면 제외 목록에
적으라고 하고, 제외 목록에만 남아 실물이 없는 항목도 잡는다.

## 경계 규칙

기능은 자기 파일을 배타로 갖는다. 두 기능이 같은 파일을 쓰면 동시에 수정할 때 같은 파일에서
충돌한다("기능은 자기 파일을 배타로 갖는다").

앱 셸은 기능을 정적으로 import 하지 않는다. 한 줄이라도 남으면 끄는 의미가 사라진다
("코어는 화면 모듈을 정적으로 끌어오지 않는다").

앱 셸이 기능의 동작을 호출해야 하면 이름으로 호출한다.

```js
// 앱 셸 쪽
import { callHook } from "../core/hooks.js";
callHook("memo.archive");
// 기능 쪽
import { provide } from "../core/hooks.js";
provide("memo.archive", () => archiveMemo());
```

없는 이름을 호출하는 것은 오류가 아니며, 그것이 이 장치의 존재 이유다. 다만 이름이 일치하지
않으면 아무 오류 없이 동작하지 않으므로, 호출하는 이름마다 채우는 쪽이 있는지 검사가 확인한다
("부르는 이름은 채우는
자리가 있다"). 반환값을 쓰는 쪽은 호출하는 쪽이 대체값을 갖는다.

서버 메시지 처리기도 기능이 들고 온다. `main.js` 표에 남겨 두면 그 기능을 꺼도 그 줄이 남아
모듈이 함께 로드된다. 같은 type 을 둘이 들고 있으면 나중에 등록된 쪽이 조용히 이긴다(검사가 확인한다).

기능의 것이 아닌 코드를 기능 안에 두지 않는다. 레포 이름(`core/repo-name.js`)과 스페이스 이름이
그렇게 잘못 배치되어 있었다. 그 결과 diff 화면이 깃을, 메모 알림이 메모 화면을 통째로 로드했다.

## 가운데 탭 기여 절차

가운데 탭은 어떤 확장자가 무엇인지 알지 못하고 `web/js/core/file-kinds.js` 표에 묻기만 한다
("가운데 탭은 확장자를 모른다"). 새 뷰어를 추가하는 기능은 자기 `initCapability` 에서 한 줄을
등록한다. 항목은 판정 · 탭 종류 · 새 탭에 세울 표시 · 글자 표현 유무 · 무엇을 어떻게 읽는가 ·
「모두 취소」가 무엇을 다시 읽어야 하는가다.

```js
registerFileKind({
  id: "sheet",                                   // 문서 탭의 종류 이름
  test: (path, tab) => SHEET_RE.test(path),      // 탭을 주면 탭 상태가 경로보다 우선한다
  tabKind: "file",                               // "docx" 면 docxview, 아니면 fileview
  tabFlags: { sheetMode: true },
  textForm: (path) => SHEET_TEXT_RE.test(path),  // 같은 파일을 글자로도 볼 수 있는가
  read: (path) => ({ type: "sheet.read", path }),
  discardReads: (path) => ({ text: false, data: true }),
});
```

표는 이것도 함께 갖는다.

```js
pending: (tab) => tab.sheet == null && tab.sheetError == null,   // 아직 받지 않았는가
tabFields: () => ({ sheetMode: false, sheet: null }),            // 이 뷰어가 쓰는 탭 칸의 기본값
docIcon: "📊", docLabel: "스프레드시트",                          // 브라우저 탭 줄과 지목 안내
```

`pending` 이 없으면 앱 셸이 `docxData`·`sheetError` 같은 다른 모듈의 칸 이름을 알아야 한다.
`tabFields` 는 모든 파일 탭이 등록된 전부를 함께 갖는다. 칸의 유무에 따라 닫기 확인의 결과가
달라지면 안 되기 때문이다("아직 못 받은 탭인지를 그 뷰어가 답한다" · "문서 탭이 무엇인지도 그 뷰어가 답한다").

등록 순서가 곧 우선순위다. 아무 뷰어도 맡지 않는 경로는 글자 파일로 처리하고, 글자로 열 수 없는
것은 Finder 로 보낸다. 그래서 뷰어를 끄면 표·문서가 빈 탭이 아니라 Finder 에서 열린다.

## 가운데 화면 기여 절차

어느 화면에 표시되는지는 `web/js/core/tab-views.js` 표가 갖는다. 앱 셸은 그 표를 돌며 영역을
만들고 그 함수를 호출할 뿐, 종류 이름을 직접 갖지 않는다("가운데 지면을 틀이 세지 않는다").

```js
registerTabView({
  kind: "diff",          // 탭의 kind 값
  panelId: "diffview",   // 그 화면의 element id. 앱 셸이 등록 뒤에 만든다
  fileLike: false,       // 이 탭이 디스크의 파일 하나를 가리키는가(감시·저장·복원이 그 값을 본다)
  render: (t) => renderDiffView(t),
});
```

영역은 등록한 뒤에 생긴다. `center/tabs.js` 의 `ensureTabViewPane` 이 `#center-body` 안에 id 와
class 가 `panelId` 인 div 를 만들고, 기능이 로드된 직후 `ensureTabViewPanes()` 가 등록된 것을 한
번에 만든다. 그래서 새 기능은 이 때문에 `index.html` 을 수정하지 않는다. 같은 id 가 이미 있으면
그 영역을 그대로 쓰므로, 앱 셸 자신의 화면(fileview·docxview)이 index.html 에 남아 있어도 두 벌이
되지 않는다.

`file` 과 `browser` 는 앱 셸의 것이라 등록하지 않는다. 같은 종류를 두 기능이 등록하면 먼저 등록된
것을 유지하고 나중 것을 거절하며 경고를 남긴다.

## 배치 영역 기여 절차

작업 화면의 영역 배치는 앱 셸의 `web/js/core/layout-engine.js` 가 정한다. 기능이 탐색기·채팅처럼
따로 놓이는 영역을 더하려면 `web/js/core/layout-regions.js` 에 등록한다. 엔진은 이 표만 읽으므로
기능 이름을 모른다.

```js
registerLayoutRegion({
  id: "emulator",               // 배치 트리에 저장되는 이름
  label: "에뮬레이터",           // 편집 모드의 이름표
  el: column,                   // 기능이 .app 에 한 번 붙인 요소. 옮기지 않는다
  visible: () => !!columnEntry, // 지금 자리를 차지하는가
  size: 360,                    // 처음 놓일 때의 폭(px). 채팅 왼쪽에 들어간다
});
```

보임이 바뀌면 기능이 `notifyLayout()` 을 부른다. 등록하지 않은 기능의 영역 이름이 저장된 배치에
남아 있어도 지우지 않으므로, 기능을 껐다 켜도 자리는 그대로다. 창 폭 820px 이하에서는 엔진이
꺼지고(body 에서 `layout-on` 이 빠진다) 등록한 영역은 보이지 않는다.

앱 셸이 기능의 동작을 호출하는 지점은 `web/js/core/hooks.js` 다. 이름은 "기능.동작" 형식이고,
앞부분이 채우는 쪽을 가리킨다. 로드되지 않은 기능의 이름을 호출하는 것은 오류가 아니며, 그
지점은 아무 동작도 하지 않는다.

## 기능을 껐을 때의 동작

rail 에서 내려가고, 순환에서 빠지고, 이름으로도 열리지 않는다. rail 버튼이 없는 기능은 자기
영역(`panel`)이 화면에서 내려간다. 내리지 않으면 아무도 채우지 않는 안내문만 남은 빈 영역이
보인다("끈 기능의 자리는 실제로 내려간다"). 한 번 로드한 ESM 은 내릴 수 없으므로 그 모듈은
즉시가 아니라 다음 재로딩부터 로드되지 않는다. 설정 화면이 그 자리에서 ⌘⇧R 을 안내한다(메인
창에서 ⌘R 은 이름 변경이다).

켜는 동작은 두 가지로 갈린다. 렌더러만 있는 기능은 아직 로드되지 않은 모듈을 그 자리에서
로드한다. 서버·네이티브 쪽이 함께 있는 기능은 렌더러만 먼저 로드하면 절반만 켜지므로 앱
재시작까지 미룬다. 상태만 저장하고 「앱을 다시 시작하면 켜집니다」로 답한다. 프리셋도 같은
규칙이고, 지금 로드하지 못한 기능은 이름을 적어 알린다.

서버와 네이티브도 같은 파일을 읽는다. 서버는 부팅에서 한 번 판정해 꺼진 행의 `init`·
`onConnect`·`handle` 을 조립하지 않고, 정적 서빙으로 응답이 새지 않도록 그 행의 HTTP 경로는
예약만 하고 404 로 답한다. 네이티브는 꺼진 기능의 모듈을 `require` 하지 않는다. 둘 다 부팅 한
번의 판정이라 재시작 전까지는 켜져 있던 구성으로 동작한다. 어느 쪽인지는 등록표의
`server`·`native` 표시가 정하고, 그 문구를 `core/features.js` 가 만든다. 검사는 그 표시가
서버·네이티브 표와 일치하는지까지만 확인하고, 화면에 그 문구가 보이는지는 검사하지 않는다.

끌 수 없는 기능은 작업(rail 이 비면 이동할 곳이 없다)과 설정(끄면 되돌릴 화면이 사라진다)
둘이다. 정책은 `canDisable`, 문구는 `disabledReason` 이다. 한 필드에 두면 문구를 고치는 일이
권한을 바꾸는 일이 된다.

메모의 서버 쪽은 꺼져 있어도 조립한다(`serverAlways`). 메모 창과 스페이스 열쇠 이관이 함께
쓰므로, 본 창에서 껐다고 저장소까지 내리면 그 창이 동작하지 않는다. 원격 창에서는 변경할 수
없고, 저장이 거절되며 목록이 읽기 전용으로 표시된다.

## 기본 꺼짐 기능(optIn)

다른 앱의 창을 옮기거나 로그인 항목을 바꾸는 것처럼 사용자가 알고 켜야 하는 기능은 기본 꺼짐으로
등록한다. 렌더러 표 항목에 `optIn: { title, items, after }` 를, 네이티브 표 항목에 `optIn: true` 를
적는다. 새로 설치한 사람과 이미 쓰던 사람 모두 그 기능이 꺼진 채로 시작한다.

상태는 `features.json` 의 `shown`(사용자가 켠 기본 꺼짐 기능)이다. 판정식은
`server/feature-state-read.cjs` 의 `featureOn` 하나이고, 렌더러 `core/features.js` 가 같은 식을
옮겨 쓴다. hidden 에 있으면 꺼짐, 기본 꺼짐 기능은 shown 에도 있어야 켜짐이다. `shown` 이 없는
옛 파일은 빈 목록으로 읽고, `shown` 을 보내지 않는 저장 요청은 기존 `shown` 을 유지한다.

- 켜기: 설정 목록의 스위치를 누르면 `items` 를 나열한 확인 창이 뜨고, [켜기] 를 눌러야 저장한다.
  `toggleFeature` 는 `confirmed` 없이 기본 꺼짐 기능을 켜지 않는다. 프리셋은 꺼진 기본 꺼짐 기능을
  켜지 않는다(켜진 것은 끈다).
- 끄기: 저장 전에 ``callHook(`${id}.disabling`)`` 를 부르고 최대 3초 기다린다. 기본 꺼짐 기능은 이
  이름을 채워 재시작 전까지 돌던 네이티브 동작(단축키·타이머·자기가 켠 로그인 항목)을 되돌린다.
- 서버 쪽 구성 요소는 가질 수 없다. 서버 부팅 판정은 hidden 만 본다.

검사: 두 표의 `optIn` 일치·확인 창 문구·서버 쪽 구성 요소 없음은 `tool-screens.mjs` 의
「기본 꺼짐(optIn)은 …」, `${id}.disabling` 을 채우는지는 「부르는 이름은 채우는 자리가 있다」가 본다.
판정·저장·확인·프리셋은 T1~T3 이 본다.

## 현재 상태와 알려진 한계

성립하는 것은 다음과 같다. 켜고 끄는 여덟 항목에 대해, 끈 기능의 진입 모듈은 다음 재로딩에서
로드되지 않는다. 그 화면은 rail 에서 내려가고 이름으로도 열리지 않으며, 영역을 갖는 기능은 그
영역도 내려간다.

아직 성립하지 않는 것도 있다. 위 내용을 "그 기능이 통째로 없어진다"로 읽으면 안 된다.

- 기능 CSS 는 항상 로드된다. 앱 셸이 index.html 에 그려 둔 영역도 항상 있다(끄면 감춰질 뿐이다).
  끄면 로드되지 않는 것은 진입 JS 와 그것이 들고 오는 rail 화면의 영역뿐이다.
  CSS 도 켤 때 로드하는 방식은 검토한 뒤 보류했다. cascade 자체는 안전하다(기능 CSS 의 이름은
  그 파일에만 있고, 패널을 감추는 것은 앱 셸의 `.rail-panel` 이라 늦게 로드해도 패널이
  번쩍이지 않는다). 문제는 아래 도크다. 메모 도크는 접힌 상태에서도 머리 바가 보이는데, 그 안의
  버튼 두 묶음을 감추는 규칙(`.panel.memo.collapsed .memo-modes`·`.memo-launches`)이 메모 CSS 에
  있다. 늦게 로드하면 앱을 켤 때마다 그 버튼들이 잠깐 보였다 사라진다. 없애려면 그 규칙을 앱
  셸로 올려야 하고, 그러면 앱 셸이 메모의 이름을 갖게 되어 소유 경계가 흐려진다.
  CSS 에 대한 정확한 표현은 "내용은 분리했고, 영역·조합·일부 전역 자원은 아직 공유"다.
  "CSS 도 기능마다 분리했다"는 주장은 성립하지 않는다. 분리된 것은 표의 css 가 그 기능의
  파일을 적고, 검사가 "그 지면이 세운 이름을 그 기능의 파일만 쓰는가"를 확인하는 부분이다.
  공유로 남은 것은 영역과 배제 행렬이다. 기능들 사이의 계약이라 03-feature-modes.css 가
  전부 갖고(설정 화면 몫도 20-keymap.css 에서 흡수했다),
  여러 화면이 함께 쓰는 껍데기는 01b-screen-chrome.css 가 가지며, 앱 셸이 그린 도크·띠 영역의
  마크업은 index.html 한 파일에 있다. 화면마다 자기 것으로 남는 폭은 각자의 CSS 가 갖는다.
- 그 소유 검사에는 한계가 둘 있다. 마크업 쪽은 `<aside>` 만 보고 두 패널 이상이 함께 쓰는
  이름만 검사해서, 한 패널만 다른 기능의 이름을 쓰는 경우와 aside 밖의 기능 DOM 은 보지 못한다.
  실제로 별도 메모 창 마크업(mw-*)이 aside 밖 index.html 에 있어 이 검사 범위 밖이다. 구역별
  소유를 검사하는 절은 해당 사례가 그 하나뿐이라 만들지 않았다. CSS 쪽은 앱 셸이 세운 이름을
  소유에서 제외하므로, 앱 셸이 참조하는 기능 이름(.ar-panel · .memo-window 처럼 03 이 배치를
  적는 것)은 보호 대상이 아니다.
- 어떤 기능은 화면만 표에 있고 실제 동작은 앱 셸에 남아 있다. 메모는 사이드바 패널·저장소·메시지가
  앱 셸에 있고 rail 화면만 기능이다. 보관은 스페이스 접기 동작이 탐색기 컨텍스트 메뉴에 남고,
  실행은 서버 쪽 실행기가 항상 있다.
  깃은 diff 까지 포함한다. devtool/diff.js · core/repo-name.js · 07b-diff.css 가
  그 기능의 것이고, git-diff 응답 처리도 그 안에서 연결한다. 끄면 변경 목록과 diff 화면이
  함께 없어진다.
- 서버·네이티브도 같은 상태를 읽는다. 서버는 등록표(`server/capabilities.js`)의 켜진 행만
  조립하고, 네이티브는 `main.cjs` 의 `isOn` 으로 꺼진 모듈을 `require` 하지 않는다. 다만 판정은
  부팅 한 번뿐이라 재시작 전까지는 변경 전 구성으로 동작한다. 서버 쪽 병렬 수정은 이렇게 갈린다.
  · 여덟 기능에 대해서는 이미 성립한다. 기존 로직은 자기 파일에서 고치고(조립부만 호출하는 서버
    파일 15개), 새 메시지 종류도 조립부를 수정하지 않는다. 깃·실행·보관은 `git.`·`run.`·`archive.`
    접두사로 통째로 넘기고, 메모는 handleMemoMessage 가 참/거짓을 돌려주는 방식이라 자기 type 을
    자기가 정한다.
  · 남은 중앙 분기는 앱 셸 몫이다. 브라우저(21개 type 을 조립부와 handler 양쪽에 중복 열거) ·
    fs · docx · sheet · workspace 가 여기 해당한다. 브라우저 쪽 중복은 handler 가 참/거짓을
    돌려주게 하면 없어진다.

소유 검사에는 한계가 하나 더 있다. 앱 셸을 "main 에서 참조되는 것"으로 정의하므로, 기능 구현을
앱 셸 파일로 옮기면 배타성 검사는 오히려 통과한다. 이 부분은 검사가 아니라 리뷰가 지킨다.

"앱 셸 파일을 호출하는 곳이 한 기능뿐이면 그것은 그 기능의 것"이라는 검사는 성립할 수 없어
만들지 않는다. 앱 셸은 main 에서 import 사슬로 참조된다는 뜻이라 그런 파일에는 언제나 앱 셸 쪽
호출자가 하나 이상 있다. 조건이 참이 되는 경우가 없으므로 그 검사는 항상 통과하고, 통과가
아무것도 보장하지 않는다. 실제로 걸린 사례는 CSS 쪽에서 잡혔다. browser/profiles.js 가 사용하지도
않는 accounts-view.js 를 import 만 하고 있었고, "이 지면의 이름을 그 기능의 파일만 쓰는가"가
그것을 짚었다. 코드 소유를 직접 판정하기 어려울 때는 그 코드가 만드는 이름을 보는 편이 낫다.

기능을 분리한 자리에는 죽은 참조가 남을 수 있고, 여기는 아직 검사가 없다. 요소 지목을 분리하면서
main 의 recordCurTarget 한 줄이 남았을 때, 문법 검사(node --check)와 나머지 검사는 모두 통과했다.
그 한 줄이 최상위 await 앞에서 예외를 던져 기능 열넷이 전부 로드되지 않았고, 렌더러를 열어서야
확인됐다.

검사를 만들려면 파서가 필요하다. 어느 이름이 이 파일 안에서 바인딩됐는지는 함수 인자·구조분해까지
봐야 판정할 수 있기 때문이다. 이 저장소에는 파서가 없다. acorn 으로 만들면 저장소가 아니라
사용자 홈의 ~/node_modules/acorn 을 참조해 이 기계에서만 통과하는 검사가 된다. 넣으려면 acorn 을
devDependency 로 추가하는 결정이 먼저다. 그때까지는 렌더러를 한 번 열어 보는 것이 유일한 확인
수단이다.

참이 될 수 없는 조건을 검사하던 자리도 있었다. "rail 없는 기능은 화면을 갖지 않는다"가 표의 그
항목에서 `return { … screen:` 을 찾았는데 표에는 return 이 하나도 없다. 항상 통과했고 그 통과가
아무것도 보장하지 않았다. 화면을 돌려주는 자리는 표가 아니라 그 기능의 입구(`initCapability`)
이므로 그쪽을 검사한다.

이름 소유에도 구멍이 있었다. 검사가 "앱 셸 CSS 가 세운 이름은 기능의 것이 아니다"로 걸러서,
다른 기능의 이름을 앱 셸 CSS 에 한 줄 적기만 해도 그 이름이 걸러져 소유 검사 전체가 무력해졌다.
이제 소유자는 "맨 이름으로 세운 규칙"(`.wvc-row { … }` 처럼 조상 없이 선 규칙)으로 정하고, 앱 셸
CSS 가 기능의 맨 이름을 세우는 것 자체를 막는다. 다른 기능의 이름에 기대는 것은 허용한다.
`body.memo-mode .memo-window` 에서 세우는 것은 memo-window 이고 memo-mode 는 앱 셸이 붙이는
body class 이며, `.memo-window .panel-head` 는 앱 셸의 껍데기를 자기 안에서 조정한다.

## 상태 계약과 공유 도구

꺼짐 상태는 렌더러 localStorage 가 아니라 설치본 상태 폴더의 `features.json` 에 있다. 그래서
렌더러·서버·네이티브가 같은 사실을 읽는다. 렌더러는 `GET /features`, 서버는 부팅 시점, 네이티브는
`isOn` 으로 읽는다. 옛 localStorage 값은 한 번 이관하고 표식을 남겨 다시 이관하지 않는다.

성립하는 것은 다음과 같다. 끈 기능은 렌더러에서 `load` 를 호출하지 않고, 서버 조립에서 빠지고,
네이티브에서 `require` 되지 않는다. 저장은 로컬 창만 할 수 있다. 두 창이 동시에 변경하면
`baseRevision` 이 일치하지 않는 쪽이 409 로 거절되고, 거절당한 쪽은 돌아온 최신 상태에 자기
변경을 다시 얹어 보내므로 서로의 변경이 남는다.

아직 성립하지 않는 것.

- 메모의 서버 쪽은 꺼져 있어도 조립한다. 그 부분을 끄는 것은 메모 창과 열쇠 이관을 함께 옮긴 뒤의 일이다.
- 서버·네이티브 판정은 부팅 한 번이다. 재시작 전까지는 변경 전 구성으로 동작한다.
- 켜기는 상태를 먼저 저장하고 그다음에 로드한다. 로드에 실패하면 실패가 표시되지만 저장된
  상태는 켜진 채로 남고, 되돌리지 않는다.
- 원격 창은 읽기 전용이다. 상태를 읽지 못했을 때는 선택 기능을 하나도 로드하지 않은 채로 뜨고
  설정만 잠긴다.

각 검사가 막는 항목.

| 검사 | 무엇을 막는가 |
| --- | --- |

## 현재 기능 목록과 코드 분포

계정 · 보관함 · 메모 · 깃(변경 목록 + diff 화면) · 로그인 · 로컬 서버 ·
사용량(창 아래 띠 + rail 화면) · 실행(rail 없이 영역만) · 표·문서 뷰어(가운데 탭에 붙는다) ·
채팅 복붙(터미널 위에만 붙는다) · Chrome 넘기기 · 로그인 저장 · 최근 닫은 탭 목록 ·
요소 지목·녹화 · 마크다운 미리보기(뒤의 다섯은 분리 브라우저 창에서도 동작한다).

rail 화면 중 앱 셸에 남은 것은 작업(rail 이 비지 않도록)과 설정(여기서 되돌리므로) 둘뿐이다.

렌더러 자바스크립트의 분포는 아래와 같다. 손으로 적은 수는 실제와 어긋나므로 아래 표는 측정
시점의 값이고, 수정할 때는 이 명령으로 다시 계산해 덮어쓴다.

```sh
node --input-type=module -e '
const {CAPABILITIES} = await import("./web/js/core/capabilities.js");
const own = new Set(CAPABILITIES.flatMap((c) => c.files.map((f) => "web/js/" + f)));
const {execSync} = await import("node:child_process");
const files = execSync("git ls-files web/js").toString().trim().split("\n").filter((f) => f.endsWith(".js"));
const tally = {};
for (const f of files) {
  const p = f.replace("web/js/", "");
  const b = p.includes("/") ? p.split("/")[0] : "main.js";
  tally[b] = tally[b] || {shell: 0, cap: 0};
  own.has(f) ? tally[b].cap++ : tally[b].shell++;
}
console.log(tally, "기능", CAPABILITIES.length);'
```

|---|---|---|
| browser | 13 | 17 |
| core | 13 | 1 |
| center | 7 | 1 |
| panel | 5 | 6 |
| devtool | 3 | 5 |
| herdr | 4 | 0 |
| explorer | 2 | 0 |
| sheet · docx · viewer · chatcopy | 0 | 18 |
| statusbar | 0 | 1 |
| usagestats | 0 | 1 |
| main.js | 1 | 0 |
| 합 | 48 | 50 |

앱 셸에 남은 48 은 기능 경계 밖의 공통 기반이다. core 는 표·훅·ws·창, center 는 탭 처리,
browser 는 브라우저 전체, panel 은 배치와 터미널이다.

자기 CSS 이름을 하나도 정의하지 않는 기능도 있다. 마크다운 미리보기가 그렇다. 그리는 화면의
이름(.md-body)을 메모도 같은 모습으로 쓰므로 그 이름은 앱 셸이 정의하고 이 기능은 참조만 한다.
그때는 표에 빈 목록(`css: []`)을 적는다. "적지 않았다"와 "없다고 적었다"는 다르므로 앞의 것만
결함이다. 빈 목록이 사실인지는 검사가 확인한다. 그 기능의 파일이 만드는 접두사 이름이 어느
CSS 에도 없으면 정의한 이름이 없는 것이 맞고, 있으면 검사가 막는다.

기능별 병렬 수정은 파일만 겹치지 않으면 되는 것이 아니다. 두 사람이 각자 기능 하나를 수정할 때
충돌할 수 있는 지점은 파일 · CSS · 훅 이름 · 서버 메시지 · rail 영역 · 패널 영역 여섯이고, 그중
하나만 겹쳐도 한쪽 수정이 다른 쪽을 덮거나 거절당한다(메시지는 나중에 등록하는 쪽이 거절당하고,
훅은 나중 provide 가 경고를 남긴다). 그래서 기능 쌍마다 그 여섯을 전부
대조한다("두 기능이 같은 자리에 손대지 않는다").

메시지 표는 그 자리에 직접 쓰거나(`ws: { … }`) 함수가 돌려주는(`ws: initMemoCapability(ctx)`)
두 형태로 적힌다. 앞 형태만 읽던 초기 검사는 메모의 열넷을 통째로 놓쳤다. 표를 들고 있다고
적혀 있는데 하나도 읽지 못하면 그 자체를 결함으로 처리한다. 조용히 0 으로 넘어가면 그 기능의
메시지가 검사 대상에서 빠지기 때문이다.

훅은 "끄면 그 지점이 아무 동작도 하지 않는다"로 성립한다. 그런데 호출하는 쪽이 반환값에 바로
접근하면(`callHook(...).foo` · `[0]` · `for…of` · 스프레드) 끈 순간 그 줄에서 예외가 난다.
채워졌을 때만 실행되는 코드라 일반 검사로는 잡히지 않고 그 기능을 끈 사용자만 만나므로, 그
형태를 막는다("훅에서 돌아온 값을 바로 파고들지 않는다"). 값을 변수로 받아 `if` 로 거르는
형태는 이 검사가 보지 못하므로 그 부분은 리뷰가 지킨다.

저장하지 않은 편집을 판정하는 코드가 앱 셸에 있었다. `center/tab-close.js` 가 `_sv*` 넷과
`docx*` 다섯을 직접 읽어 dirty 를 판정했고, 되돌릴 때 표 상태 열셋을 직접 비웠고, 탭이 사라질
때 표의 인라인 편집기를 정리했다. 시트 모듈은 그 판정을 다시 앱 셸에서 `import` 했다. 칸을
만드는 곳과 판정하는 곳이 갈라져 있었고, 새 뷰어를 추가하는 사람이 앱 셸의 dirty 판정까지
수정해야 했다. 훅 이름 일곱 개로 분리했다.

`viewer.tabDirty` 는 어느 뷰어가 들고 있든 미저장 편집이 있는지를, `viewer.sheetTabDirty` 는 표만
판정한다. `viewer.discardSnapshot`·`viewer.sameDiscardSnapshot`·`viewer.resetAfterDiscard` 는
되돌리기의 세 단계이고, `viewer.tearDownTab`·`viewer.retargetTabPath` 는 탭이 사라지거나 옮겨질
때 쓴다. `viewer.saveTab` 은 이 탭의 저장을 누가 맡는지 답하며, `undefined` 가 뷰어의 것이
아니라는 뜻이다. 그때만 앱 셸이 자기 방식으로 저장한다. 표 판정은 `sheet/edit.js`, 문서 판정은
`docx/editor.js`, 탭에 붙은 표 상태는 새로 만든 `sheet/tab-state.js` 가 갖는다.

비교가 답을 주지 못하는 경우는 fail-open 으로 뒀다. 뷰어가 로드되어 있지 않으면 비교할 상태도
없으므로, 명시적으로 `false` 를 답할 때만 달라진 것으로 판정한다. 반대로 두면 뷰어를 끈
사용자의 글자 탭 되돌리기가 항상 취소된다.

분리하면 새 사각지대가 생긴다. 소비 쪽 검사는 앱 셸이 이 이름을 호출하는지 보고 구현 쪽 검사는
그 함수가 어떻게 판정하는지 보는데, 그 이름을 다른 함수에 연결해도 둘 다 통과한다.
`provide("viewer.tabDirty", () => false)` 하나로 표·문서의 미저장 편집이 조용히 clean 이 된다.
분리의 대가로 생긴 틈이므로 `SEAM-1` 이 이름 여덟과 그것을 호출하는 함수 열을 짝지어 막는다.
그 검사가 확인하는 것은 그 이름이 그 함수를 호출한다는 사실까지다.

목록을 손으로 적은 검사 둘도 같은 문제였다. 되돌릴 때 비우는 칸을 넷만 적어 둬서 나머지 아홉을
지워도 통과했고, 스냅숏 비교는 검사 대상이 아니어서 `return true` 로 바꿔도 통과했다. 둘 다
파생 방식으로 바꿨다. 시트가 탭에 쓰는 칸을 전부 뽑아 "비우는 것"과 "의도적으로 남기는 것"으로
나누고 어느 쪽에도 없으면 막는다(보기 상태 열여섯은 남기는 쪽이다. 되돌리기는 내용을 되돌리는
것이지 사용자가 보던 위치를 옮기는 것이 아니다). 스냅숏이 만드는 칸도 뽑아 비교가 그 이름을 다
쓰는지 확인한다. 칸이 하나 늘면 검사가 그 자리에서 결정을 요구한다.

`center/tabs.js` 도 같은 문제였다. 화면 전환에서 `docxEditor.detach()`·`docxDirty`·`_svEd`·
`_svFxEd`·`sheetIdx` 를 직접 변경했고, `applySheetResponseData` 라는 표 전용 함수가 통째로 앱
셸에 있었고, 저장 목록은 `sheetMode` 라는 칸 이름으로 걸렀다. 훅 이름 셋으로 분리했다.
`viewer.leaveTab`(내려가는 탭이 자기 상태를 정리한다) · `viewer.enterTab`(올라오는 탭이 어느
시트를 펼지 받는다) · `viewer.presentsTab`(지금 뷰어가 그리고 있는가)이다. 표 전용 함수는
`sheet/tab-state.js` 로 옮겨 `svApplyResponseData` 가 됐다. 호출하는 쪽이 뷰어 하나뿐이라 훅을
만들지 않고 그대로 내준다.

호출 순서가 결과를 바꾸는 지점이 있다. 내려가는 탭의 편집기를 먼저 커밋하고 그 뒤에 새 시트
번호를 설정한다. 순서가 반대면 아직 커밋하지 않은 편집이 이미 바뀐 시트 번호로 판정되어 조용히
버려진다. `T-B1-8` 이 그 순서를 검사한다.

앱 셸에 남은 것은 `switchSheetMode` 의 `sheetMode` 하나다. 그 함수 자체가 표와 글자를 전환하는
토글이라 이름부터 표의 것이고, 옮기려면 되돌리기 대화상자와 함께 옮겨야 해서 따로 다룬다.
`center/tabs.js` 의 `acceptDocxReadRevision` 은 이름만 문서의 것이고 구현은 앱 셸에 있었다.
호출하는 쪽이 뷰어 하나뿐이라 함수를 없애고 뷰어가 자기 칸을 직접 쓴다. `center/text-editor.js`
는 `if (t.sheetMode)` 로 표인지 판정한 뒤 표 그리기를 호출했다. 이제 `viewer.renderBody` 하나를
호출하고, 그린 쪽이 참을 돌려주면 거기서 멈춘다. 앱 셸은 어느 뷰어인지도, 그 뷰어가 어떤 칸으로
자기를 판정하는지도 알지 못한다.

`browser/dock.js` 는 아직 `docxEditor`·`docxDirty`·`_svEd` 를 직접 변경한다. 같은 종류의 문제이고
아직 남아 있다.

## 앱 셸이 기능 이름을 참조하는지 검사하는 방법

「가운데 지면을 틀이 세지 않는다」가 이 계약을 검사한다. 손으로 적는 목록이 하나도 없다.

검사 대상 파일은 등록표가 어느 기능에도 할당하지 않은 렌더러 파일 전부다. 이전에는 다섯 개를
손으로 적었고, 그 밖의 파일은 무엇을 하든 검사되지 않았다.

금지어는 등록된 종류 이름(`fileKinds()` 의 id 와 `registerTabView` 의 kind)과 그 뷰어가
`tabFields()` 로 선언한 칸 이름이다.

예외는 이유와 함께 검사 안에 적는다. 현재 둘이다. `browser/dock.js` 는 아직 옮기지 않았고,
`center/tab-close.js` 의 `switchSheetMode` 는 이름부터 표의 것이다. 전부 고쳤는데 예외 목록만
남는 것도 막는다. 그 파일이 그 이름을 이미 쓰지 않으면 검사가 실패한다.

### 파생할 수 없는 목록

「채팅 복붙을 틀이 모른다」의 금지어 열셋은 파생 대상이 아니다. 그 기능의 내부 이름이라
export 도 아니고, 최상위 선언을 전부 뽑으면 주입받는 이름(`showToast`·`esc`·`wsSend`·`dom`)까지
걸려 대부분이 잡음이 된다. 걸리는 것의 대부분은 주입 경계 양쪽에 같은 이름이 있는 정상 상태다.

그래서 이 목록은 손으로 적되 반대 방향으로 오래되는 것을 막는다. 금지어가 그 기능에서 사라지면
그 줄은 그때부터 아무것도 검사하지 않는다. `registerTerminalCopyFormatters` 가 그렇게 검사 줄에만
남아 있었다. 그래서 금지어가 그 모듈 집합에 실제로 있는지 단어 경계로 함께 확인한다. 부분
문자열로 검사하면 `cropAwareSelection` 을 `cropAwareSelectionX` 로 바꾸는 것을 잡지 못한다.

이 하나만 아무것도 검사하지 못했던 이유는 검사의 방향이다.

존재를 검사하는 목록은 이름이 바뀌면 그 자리에서 실패해 스스로 알린다.
부재를 검사하는 목록은 이름이 바뀌면 조용히 통과하고, 죽은 줄이 그대로 남는다.

그러므로 "없어야 한다"를 손으로 적은 자리에는 그 이름이 아직 있는지 함께 확인하는 절이 붙어야
한다. "있어야 한다"에는 필요 없다.

검사가 스스로 무력해지는 경로도 막았다. 이 검사의 근거는 뷰어의 선언이므로, 뷰어가
`tabFields()` 를 비우면 그 칸들이 파생에서 빠져 앱 셸이 무엇을 하든 통과한다. 그래서 종류마다
한 칸이라도 선언하는지 함께 확인한다.

파일 이름을 손으로 적어 둔 목록은 그 자체가 사각지대다. "가운데 탭은 확장자를 모른다"는 앱 셸
네 파일만, "채팅 복붙을 틀이 모른다"는 세 파일만 검사했고 목록 밖은 검사되지 않았다. 둘 다
등록표에서 파생한 앱 셸 전체로 넓혔고, 그때 세 곳이 드러났다. `browser/pick.js` 가 뷰어의 종류
이름("docx")을 직접 참조했고, `center/file-routing.js` 는 종류를 찾지 못하면 "sheet" 로 처리했고,
`center/tab-close.js` 는 지금도 시트 뷰어의 내부 상태(`_sv*` 열셋)를 되돌린다. 앞의 둘은 막았다.
`viewer.activeDocxTab` 이 생겨서 문서 화면의 소유자를 뷰어가 답하고(시트는 `activeSheetTab` 으로
이미 그렇게 하고 있었다), 라우팅은 종류를 찾지 못하면 글자 파일로 보낸다. 세 번째는 이름 열셋이
걸린 별도 사안이라 따로 다룬다.

넓힌 목록에는 검사 대상 파일 집합의 하한을 함께 뒀다. 필터가 파일을 전부 걸러내면 검사할 것이
없어서 통과하기 때문이다.

"켠 것만 싣는다"는 오랫동안 입구 파일 하나만 검사했다. `load` 가 호출하는 파일을 참조하는 다른
경로가 없는지만 보았고 그 모듈 집합의 나머지 파일은 검사하지 않아서, 파일이 여럿인 모듈 집합은
내부 파일로 우회됐다. 앱 셸이 `browser/record.js` 를 정적으로 참조하면 pickrec 은 꺼도 로드되는데,
입구인 `pick-boot.js` 는 참조가 없으므로 검사가 통과했다. 지금은 모듈 집합의 파일을 전부
검사한다. 입구는 아무도 참조하면 안 되고, 내부 파일은 같은 모듈 집합 안에서만 참조할 수 있다.
`load` 가 자기 파일 목록 밖을 호출하는 것도 함께 막는다.

아직 기능이 아닌 것.

- 브라우저는 전체로는 여전히 앱 셸에 가깝다. 앱 셸의 아홉 파일이 브라우저의 열여덟
  파일을 서른아홉 번 정적으로 참조하고, 그중 여섯이 browser/state.js 하나를 참조한다. 가운데 탭
  처리와 keynav 가 거기 의존하고, 분리 브라우저 창이라는 창 모드가 따로 있다. 분리되는 것은
  전체가 아니라 그 안의 부가 기능들이고, 창 필드가 생긴 뒤로 그 경로가 열렸다.
  분리된 것은 Chrome 넘기기 · 로그인 저장 · 최근 닫은 탭 목록 · 요소 지목·녹화다.
  요소 지목과 녹화는 한 항목으로 등록했다. 지목이 녹화에 줄을 밀어 넣고(pick.js → recPush) 녹화
  중에는 지목이 다르게 기록되므로, 나누면 둘 중 하나만 끈 사용자가 절반만 기록된 결과를 얻는다.
  앱 셸에서 호출하던 지점 넷(main · touch-drag · dock · webview-factory)은 전부 훅이 됐고,
  ws 소유 열하나도 함께 옮겼다.
  ⌘⇧T 는 함께 분리하지 않았다. 복원 스택은 앱 셸의 것이라, 목록을 꺼도 맨 위 하나를 복원하는
  경로는 남는다. 분리한 것은 그 아래 항목을 고르는 화면이다.
- 표에 계층이 없다. 계정 · 로그인 저장 · 자동완성 · Chrome 넘기기는 브라우저의 하위인데
  평평하게 등록되어 있다. 설정 목록이 길어질수록 이 구조는 읽기 어려워진다.

## 검사 대상 파일 집합의 경계

검사가 함수를 찾는 파일 집합은 `sources.mjs` 가 정한다. `web`(= index.html + main.js)은 옛
모놀리스 시절의 렌더러 전부였고 지금은 아니어서 모듈로 분리된 함수를 찾지 못한다. 함수의 구현을
확인하는 검사는 `renderer`(index.html + `web/js` 전체)를 본다. 대상 집합이 조용히 줄어드는 것은
하한(60 파일)으로 막는다.

넓힌 집합에는 대가가 있다. 앱 셸과 기능이 같은 이름의 함수를 각자 쓸 수
있다(`fileviewClickHandler`: 앱 셸은 글자 탭용, 뷰어는 문서·표용). 이름으로 찾을 때 먼저 나오는
것을 집으면 조용히 다른 것을 검사한다. 그래서 `docxSourceFunction` 은 정의가 둘 이상이면 멈추고
어느 파일인지 지정하라고 요구한다. 그런 검사는 `capabilitySource("viewer")` 로 그 모듈 집합만
본다. 어느 파일이 어느 기능의 것인지는 등록표가 갖는다.

"지금은 겹치는 이름이 없다"고 문서나 주석에 적어 두지 않는다. 그 문장은 곧 실제와 어긋나고,
멈추는 쪽은 그렇지 않다.

CSS 규칙을 보는 검사는 `allCss` 로 넓히지 않는다. 넓히면 그 규칙이 어느 파일에 있든 통과해서
소유를 판정하지 못한다(「allCss 는 음성 조건에만 쓰인다」가 그것을 막는다). 소유 파일 하나를
대상으로 한다.

## 기능 추가 시 함께 수정하는 파일

끄는 쪽은 수정할 것이 없지만 추가하는 쪽은 그렇지 않다. rail 화면 하나를 추가할 때 그 기능만
갖는 파일은 둘이다.

  web/js/<그것>/boot.js
  web/css/<번호>-<그것>.css

그 밖에, 두 사람이 각자 기능을 하나씩 추가할 때 함께 수정하는 파일.

  core/capabilities.js           한 줄     렌더러 등록표: 설계상 의도한 위치
  core/rail-items.js             한 줄     rail 표: 순서가 index.html 과 같아야 한다
  index.html                     두 군데   CSS link(번호순) · rail 버튼(순서)
  docs/iris-screens.json         한 줄
  docs/iris-sequential-audit.md  한 절
  server/capabilities.js         한 줄     서버 쪽 구현이 있을 때만
  native/electron/capabilities.cjs  한 줄  네이티브 쪽 구현이 있을 때만

rail 화면의 영역 마크업은 기능이 `panelHtml` 로 들고 오므로 index.html 에서 제외했다. 앱 셸이
그려 둔 도크·띠 영역은 그대로 남아 있고, 그것을 쓰는 기능은 등록표의 `panel` 로 그 id 를
가리킨다. 화면 카탈로그와 점검표도 순번 대신 화면 이름을 키로 쓴다. 가운데에 하나를 넣어도
뒤 항목의 번호가 밀리지 않아, 두 사람이 같은 날 화면을 하나씩 추가해도 번호 재배정으로
충돌하지 않는다. 나머지는 전부 한 줄씩이라 서로 다른 줄이면 병합된다.

다른 저장소로 전달할 때는 이 위치들을 손으로 대조하지 않는다. `bin/capability-share.mjs check`
가 받는 쪽에서 id·rail·CSS 파일·WS 접두사·HTTP 경로 충돌을 항목별로 알린다.

rail 버튼 마크업은 생성기(`railButtonsMarkup`)가 있는데도 index.html 이 정적 사본을 갖는다.
의도한 구성이다. 런타임에 교체하면 앞선 초기화 하나가 예외를 던졌을 때 rail 이 영구히 빈 채로
남는다(rail.js 머리말). 검사가 사본과 생성기 출력을 글자 단위로 대조한다.

rail 버튼을 누르면 body class 가 붙고 영역이 표시되며, 그 기능의 JS 와 CSS 만 그때 받아 온다.
로드 자체는 계약대로 동작하고, 남은 문제는 추가 전에 수정해야 하는 파일 수다.

## 모듈 그래프 기반 재검사

「켠 것만 싣는다」는 소스 문자열로 import 를 검사한다. 형태를 하나 빠뜨리면 조용히 우회되므로
부작용 import, 홑따옴표, `new Worker(`, HTML 의 `<script src>` 를 차례로 추가했다. 다음에 빠뜨릴
형태를 미리 알 수 없어서 패턴을 넓히는 것으로는 끝나지 않는다.

그래서 같은 것을 문자열이 아니라 esbuild 가 실제로 해석한 모듈 그래프로 한 번 더 검사한다
(`묶어 보면 틀에서 기능으로 가는 정적 길이 없다`). 어떤 형태로 적었든 그 도구가 참조한 것이 곧
앱에 로드되는 것이다. esbuild 는 이미 devDependency 라 추가할 것이 없다.

세 가지를 검사한다.

  앱 셸에서 기능으로 가는 정적 참조 0: 하나라도 있으면 끄는 의미가 없다
  기능에서 다른 기능으로 가는 정적 참조 0: 기능별 병렬 수정이 여기서 성립한다
  기능으로 들어가는 동적 참조의 출발은 등록표 하나: 다른 곳에서 호출하면 표가 사실이 아니게 된다

문자열로 검사하는 기존 검사는 그대로 둔다. 그래프는 `main.js` 에서 출발하므로 HTML 이 고전
스크립트로 로드하는 경로는 보지 못한다. 둘이 서로 다른 범위를 덮는다.

하한도 설정했다. 입력 60 미만 · 기능 소유 20 미만 · 동적 참조 5 미만이면 검사 대상 파일 집합이
잘못 좁혀진 것으로 보고 멈춘다.

## 검사 패턴의 범위

검사가 예전 코드 형태를 요구하면 훅과 등록표 뒤로 옮겨간 계약을 보지 못한다. 그런 검사는 사슬을
양쪽에서 확인하는 방식으로 바꾼다. 앱 셸이 이름을 호출하는가와 그 이름을 채운 쪽이 실제로 그
동작을 하는가를 함께 본다. 한쪽만 확인하면 다른 쪽이 빠져도 통과한다. 목록을 요구하던 검사가
순서를 요구하는 검사로 바뀌기도 한다. `BINARY_RE` 는 `.docx` 가 그 목록에 그대로 있고 등록표가
그 앞에 오기 때문에 안전하므로, 목록이 아니라 순서를 검사한다.

"이 지점 근처에 이것이 있는가"를 문자열 범위로 확인하는 검사는 그 범위가 주석으로 차면 코드가
정상인데도 실패한다. 확인 전에 줄 전체가 주석인 줄을 제외한다(`docxCodeOnly`). 반대로 범위가
넓으면 지키려던 코드를 지워도 통과한다. `renderedFileOwner` 는 그 이름이 함수 아래에서도
호출되어 비활성 판정을 통째로 지워도 통과했다. 범위는 그 동작을 하는 지점 바로 앞까지 좁힌다.

존재를 확인하는 검사는 범위가 넓을수록 약해진다. 넓은 범위는 관대해 보이지만 아무것도 확인하지
못하는 쪽으로 변한다.

## 네이티브 쪽 경계

렌더러는 표의 `load` 가 동적 import 라 경계가 있었다. 경계가 있으면 어떤 파일이 그 기능의
것인지를 사람이 아니라 그래프가 정한다. 경계를 끊고 탐색해 참조되지 않으면 그 기능의 것이다.

네이티브에는 그 경계가 없었다. `main.cjs` 가 마흔 개를 최상위에서 `require` 했고, 어떤 파일이
어느 기능의 것인지 코드에서 뽑을 방법이 없었다. 뽑을 수 없으면 표에 무엇을 적든 대조할 대상이
없어서, 빠뜨려도 없는 것을 적어도 검사가 알지 못한다.

`native/electron/capabilities.cjs` 가 그 경계를 세운다.

```
NATIVE_CAPABILITIES = [
  { id: "detachtab", module: require.resolve("./detached-tab-window.cjs") },
]
```

경로는 `require.resolve` 로 적는다. 이 형태는 모듈을 실행하지 않고 가리키기만 하므로 표를 읽어도
아무것도 로드되지 않는다. 동시에 `bin/graph.mjs` 가 그 참조를 인식한다. 문자열로만 적으면 어떤
도구도 그것을 참조로 읽지 못해서, 그 모듈이 고아로 판정되거나 소유 판정에서 조용히 빠진다.

`capability-host.cjs` 가 표를 돌며 켜진 것만 `require` 하고 `initCapability(ctx)` 를 호출한다.
기능은 자기 연결 코드를 자기가 들고 온다. 앱 셸이 팩토리를 호출하고 IPC 를 등록하던 부분이
기능으로 옮겨 갔다. 그래야 기능을 제거할 때 앱 셸을 함께 수정하지 않는다.

### 검사 항목

세 가지다. 하나만 빠져도 경계는 이름뿐인 것이 된다.

| 검사 | 무엇을 막는가 |
| --- | --- |
| 네이티브 표의 기능은 자기 배선을 들고 온다 | 연결 코드가 여전히 앱 셸에 남아 있는 상태 |
| 네이티브 기능은 표를 통해서만 실린다 | 표에도 적히고 앱 셸도 참조하는 상태. 꺼도 사라지지 않는다 |
| 네이티브 기능 id 는 렌더러 표의 id 와 같은 낱말이다 | 한 기능이 두 이름을 갖는 것 |

가운데 검사는 처음에 잘못 설계했다. 경계를 끊고 탐색해 앱 셸이 직접 참조하는지를 확인했는데,
끊은 지점을 건너뛰므로 잡으려던 상태를 볼 수 없는 형태였다. `main.cjs` 에 최상위 `require` 를
다시 넣어도 통과했다. 끊어야 하는 것은 경계가 아니라 표다. 표를 끊고도 참조되면 표 없이도
로드된다는 뜻이다.

### 켜짐·꺼짐 상태의 반영

끄고 켜는 집합은 렌더러의 localStorage 가 아니라 상태 폴더의 `features.json` 에 있고, `main.cjs`
가 `readFeatureState`·`featureOn` 으로 같은 파일과 표의 `optIn` 을 읽어 `isOn` 을 만든다. 꺼진 기능은 `require` 조차 되지
않는다. 판정은 부팅 한 번이라 변경한 뒤에는 앱을 다시 시작해야 한다.

서버에도 같은 경계가 있다. `server/capabilities.js` 가 그 표이고, 켜진 행의 `init`·
`onConnect`·`handle`·`http` 만 조립한다. 아직 적용되지 않은 것은 그 표 밖이다. 브라우저·fs·docx·
sheet·workspace 는 여전히 진입점이 정적으로 참조하는 앱 셸 몫이다.
